Information Security Policy

Version 1.1 · Effective October 29, 2026 · Next review October 2027 · Policy owner: Mathew Gutierrez, sole operator and security owner

This is the public summary of Tallyho's Information Security Policy. It describes every control the full policy requires. Operational details that would only help an attacker, such as file locations, system names and exact limits, are kept in the private version.

1. Purpose

This policy sets out how Tallyho protects the consumer financial data it receives through Plaid. It is the governing document for Tallyho's access control, data retention and privacy commitments.

2. Scope

Tallyho is a single-user application. It runs only on the operator's own computer and serves no other customers. The only consumer whose data it holds is the operator. This policy covers:

  • the application code, kept in a private source-code repository
  • the Tallyho data store and its encrypted backups
  • Plaid API credentials and the credentials Plaid issues for each connected institution
  • every account that can reach any of the above: the operator's computer login, the Plaid Dashboard and the source-code host

3. Roles and responsibilities

Tallyho has one person, who holds every role: security owner, developer, administrator, and the only data subject. Tallyho has no employees, contractors or third-party administrators, and no one else is given access to its systems or data.

If that ever changes, this policy will be revised before access is granted, adding named roles, least-privilege access and an offboarding procedure that removes access on the day a person leaves. See Access Control.

5. Access control policy

This section is Tallyho's access control policy. The roles and the permissions each one holds are defined in Access Control.

5.1 Principles

  • Deny by default. No one has access to any Tallyho system or data unless this policy grants it.
  • Least privilege. Each role gets only the permissions its task needs. Day-to-day use of the application does not need the Plaid credentials or encryption keys.
  • Personal accounts. Every account belongs to one named person. Accounts and credentials are never shared.
  • Separate environments. Development and testing use Plaid's sandbox and made-up demo data only. Production credentials are held only by the owner and administrator roles.

5.2 Network access

  • The Tallyho interface listens only on the computer's internal loopback interface and is never exposed to the internet or the local network.
  • Requests from other websites open in the browser are refused, which blocks cross-site requests and DNS-rebinding attacks.
  • Tallyho provides no remote access. No VPN, port forwarding, tunnel or remote-desktop service may be set up to reach it.
  • The only outbound connections that carry consumer data go to Plaid, over TLS.

5.3 Authentication

  • Passwords. Every account in scope uses a unique, long password kept in a password manager and never reused.
  • Multi-factor authentication on internal systems. MFA is required on every account that can reach consumer data or the credentials that fetch it: the Plaid Dashboard, the operator's platform account and the source-code host. The computer login uses a password plus biometric unlock backed by secure hardware.
  • Multi-factor authentication on the application. The Tallyho interface, where Plaid Link runs, requires a password plus a time-based one-time code from an authenticator app before it shows any data or opens Plaid Link. The server itself refuses every data and Link request without a signed-in session. Sessions expire after a period of inactivity and after a maximum lifetime, each code works only once, repeated failed attempts temporarily lock sign-in, and single-use recovery codes cover a lost authenticator.
  • Device lock. The computer requires a password to log in and to wake from sleep, and locks automatically after a short idle period.

5.4 Privileged access

  • Privileged actions are rotating Plaid credentials, moving to production, enabling Plaid products, exporting or replacing encryption keys, and restoring backups. Only the owner and administrator roles may perform them.
  • Secrets are never displayed in the interface, returned by the application, written to logs, or pasted into messages, tickets or screenshots.
  • Tallyho and its scheduled jobs run as a standard user, never with administrator rights.

5.5 Granting, changing and removing access

  • Access is granted only by the owner, only to a named person, and only after the access control document records the role and the reason.
  • When a person's role changes or they leave, the owner removes their access on the same day and rotates every secret they could have seen.
  • Tallyho currently has no one to grant access to, so no access has ever been granted or removed.

5.6 Review and exceptions

  • All access is reviewed at each annual policy review, whenever a device, account or credential changes, and after any incident. Anything this policy doesn't allow is removed straight away.
  • There are no exceptions. Any exception needs the owner's written approval, with a reason and an end date.

6. Encryption

  • At rest. The computer's disk is fully encrypted. Connection credentials issued by Plaid are encrypted a second time with authenticated encryption, using a key held in the operating system's protected credential store rather than next to the data. Backups are encrypted the same way. The application password is stored only as a salted, memory-hard hash.
  • In transit. All communication with Plaid uses TLS 1.2 or later through Plaid's official client library, with certificate verification on. Traffic between the browser and the Tallyho interface never leaves the computer.

7. Secrets management

  • Plaid credentials are stored readable only by the operator's account and are excluded from source control.
  • Connection credentials are never logged, displayed or returned by the application.
  • If a secret may have been exposed, it is rotated straight away and the incident procedure in section 11 applies.

8. Data retention and deletion

Tallyho stores only what its features need. Disconnecting an institution revokes its access at Plaid and deletes its data, and deleted data leaves the rotating encrypted backups within about two weeks. See the Data Retention and Deletion Policy.

9. Secure development

  • Source code lives in a private repository. Secrets and data files are excluded from it.
  • Changes pass the automated test suite before use.
  • Dependencies come from the official package index into an isolated environment and are reviewed and updated at least every quarter.
  • New Plaid products are enabled deliberately, and the application only requests data for products a connection already has.

10. Endpoint security

  • Automatic operating-system security updates are on.
  • The system firewall is on.
  • No one but the operator uses the computer.

11. Incident response

If data or credentials may have been exposed, the operator:

  1. Contains it: rotates the Plaid credentials, removes the affected connections and stops the application.
  2. Assesses it: works out what was exposed, when and how.
  3. Notifies: informs Plaid at security@plaid.com within 72 hours of confirming an incident that involves Plaid data or credentials.
  4. Recovers: fixes the cause, reconnects the institutions and restores from an encrypted backup if needed.
  5. Records it: writes up the incident and the fix in the policy's review notes.

12. Vendor management

Plaid is the only vendor that supplies consumer data. Tallyho uses no hosting provider, analytics service or other third-party processor of consumer data. The only other recipient is the one disclosed in the Privacy Policy.

13. Review and changes

This policy is reviewed every year and updated whenever Tallyho's architecture, data or people change. Each version is kept in version control.
